# Workflow 与 Leader-worker：真实模型轻量对比

日期：2026-10-23（北京时间）。被测提交：`fda0fd0a007ef286683abac085500bfbf8ddf2fa`。

## 结论

两个场景、两种架构，共4次真实任务，全部通过。正常填写的6个关键单元格和指定留空区域均正确，两份产物的全部表格单元格文本也相同。日期冲突时，两者均请求用户确认，没有返回生成产物。

本次样本中Leader-worker耗时与Token较低；未观察到准确性差异。每场景仅执行1次，不能据此推出任意模板上的准确率或稳定性能优势。

## 测试条件

- 模型：同一个DeepSeek官方端点、`deepseek-flash`，关闭思考模式；主Agent温度0.3、最大输出4096。保留两种实现各自的提示词、工具和内部调用设置，测试当前实现整体，不是只更换调度器的消融实验。
- 运行：本地Windows/Python 3.13；本地文件存储、内存checkpoint。相同业务指令、模板和材料；每次新建独立会话，会话ID不同。
- 任务顺序：正常填写workflow → 正常填写leader_worker → 日期冲突workflow → 日期冲突leader_worker。没有失败后择优重跑。
- 每任务上限180秒；计时覆盖图初始化、模型/网络、工具和本地文档处理。主流程使用真实模型，未注入脚本模型或离线答案。
- Token由模型返回的usage_metadata累计，四次均完整。表中总Token为输入加输出，未换算费用；缓存命中和计费价格未单独统计。
- 数据来自仓库示例，不包含用户业务资料。密钥只从本地忽略的.env读取，未写入报告或提交。

运行命令（在projects下）：


## 实际行为与产物检查

- 正常填写：Leader执行`inspect_template → extract_documents → match_fields → commit_proposal → validate_document → generate_document`，提交8项数据，无候选错误、无工具失败、未耗尽预算。
- 日期冲突：Leader仅执行模板分析和材料提取，根据结果中的冲突立即列出两个来源及不同日期并追问；没有继续调用匹配和生成。提取两份材料的Worker在同批中并发运行。
- workflow日期冲突的最终回复来自生成Agent，它也正确暂停并给出确认选项。当前流程经过更多Agent调用，这是本例Token差异的一个实际原因；调度之外还存在提示词、上下文体积和输出长度的差异。
- 两份正常填写产物ZIP CRC检查通过，python-docx重新读取成功，均为1张表、9行；全部表格单元格文本完全相同。未执行逐页视觉渲染验收。

## 判断边界与下一步

当前证据支持继续保留Leader-worker实验分支：它在这两项任务中达到与旧版相同的验收结果，尤其在冲突出现时减少后续工作。没有发现需要立即修改运行代码的失败。

本次单次、固定顺序执行，模型随机性、服务负载、导入初始化与供应商缓存均可能影响耗时；Token完整但不等于实际费用。尚未对复杂行组、长材料、同义字段冲突、用户确认后的多轮继续以及更多模板做真实A/B，不切换默认架构。

下一轮优先增加一个“冲突确认后继续生成”多轮案例，再选择包含行组的模板；若需要稳定性能结论，再做交替顺序的多次重复测量。
